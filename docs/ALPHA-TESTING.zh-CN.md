# Public Alpha 实测指南

Hippocampus v0.1-alpha 现在最需要的不是更多“看起来能用”的演示，而是真实 Agent 在连续几天使用后暴露出来的问题。

如果你已经长期使用 Hermes 或其他 coding agent，经常跨 Session 工作，这份指南可以帮你做一次有价值的实测。

## 什么样的用户最适合测试

如果你遇到过下面这些问题，你的反馈会很有价值：

- Agent 明明前几天踩过的坑，换个 Session 又重新踩一次；
- 重要项目决定总要重新解释；
- `MEMORY.md` 或类似文件越写越满，什么都想保留；
- 已经废弃的旧结论还会被重新召回；
- Session Search 能找到历史，但 Agent 并不会在合适的时候想起正确的那一段；
- 你希望“真正发生过的历史”和“模型后来总结出的记忆”能够分开保存。

如果你的需求只是让 Agent 永久记住少量稳定偏好，Hermes 自带的 `MEMORY.md` / `USER.md` 可能已经更简单。

## 先说明 Alpha 边界

当前 Public Alpha 最适合验证的是**原始来源持久化 + 显式记忆写入和召回**。

不要假设 Observer/E1 已经可以自动、稳定地把普通对话变成高质量长期记忆。这些自动记忆路径仍然属于实验能力。

测试前建议先看：

- [`PUBLIC_ALPHA_SUPPORTED_SURFACE.md`](PUBLIC_ALPHA_SUPPORTED_SURFACE.md)
- [`KNOWN-LIMITATIONS.md`](KNOWN-LIMITATIONS.md)
- [`INSTALL.md`](INSTALL.md)

## 建议跑 3～7 天，而不是聊十分钟

最好选择一个你真的在做的项目，而不是专门为了测试造一段“我喜欢咖啡”的对话。范围不必很大，但你自己必须知道哪些结论是真正有效的。

测试期间可以刻意制造下面五种情况。

### 1. 一个长期有效的项目决定

显式保存一条后续 Session 仍然应该成立的约束。

例如：

> Retrieval 的任何修改都必须保持 SQLite / PostgreSQL parity。

几天以后，在相关任务里观察 Agent 是否能够重新获得这条约束。

### 2. 一个后来被推翻的旧决定

先留下旧方案，之后在真实项目里明确换成新方案。

真正有价值的问题不是“两个都能不能搜出来”，而是 Agent 会不会把已经失效的旧决定仍然当成当前事实，能不能区分“历史上曾经正确”和“现在仍然正确”。

时间状态、supersession 等问题仍然是 Hippocampus 后续需要继续解决的部分，所以这里的失败尤其有价值。

### 3. 一个稳定的用户或工作流偏好

保存一条跨 Session 应该继续有效的偏好或工作原则。

除了看它能不能召回，还要观察它是否只在真正相关时出现，而不是变成每次任务都往上下文里塞的噪音。

### 4. 一次“原始经历”和“后来解释”可能不同的情况

找一段 Agent 很可能会误解、概括过度或者随着后续信息需要重新解释的对话。

以后检查：即使派生记忆形成得不好，是否仍然能够回到原始来源，而不是只能看到模型自己以前写下的总结。

这也是 Hippocampus 坚持把 source 和 derived memory 分开的原因之一。

### 5. 重启之后是否还在

重启相关进程，再确认显式记忆是否能够正确读回。

如果你熟悉 PostgreSQL，也可以在 disposable 环境里按文档实际跑一次 backup / restore，再检查恢复后是否还能继续写入和召回。

## 最值得记录什么

不需要专门写 benchmark。每次出现值得注意的情况，记录下面这些就够了：

- 你认为 Agent 应该记住什么；
- 实际召回了什么；
- 是没想起来、想错了、重复了，还是召回了已经过期的内容；
- 能不能追溯回原始来源；
- 是不是只有换 Session / 重启后才出现；
- Hippocampus commit / 版本和 Hermes 版本；
- 如果相关，使用的 LLM / embedding / rerank 配置。

一次**糟糕的召回**通常比十次“它成功记住我的偏好”更有价值。请不要为了让结果看起来漂亮而先替系统整理问题。

## 什么算好反馈

有价值：

> 第二天把部署目标从 A 换成了 B。第四天 Agent 同时召回 A 和 B，并且把 A 当成当前方案。这是当时的查询和返回结果。

有价值：

> 重启以后显式记忆还在，但新 Session 只有输入完全相同的关键词才能找回来，语义相近的问题没有召回。

信息不足：

> Memory 不太好用。

信息不足：

> 我试了一次，能记住偏好，挺好。

## 隐私

不要在公开 Issue 中粘贴 API Key、DSN、私有仓库代码、私人聊天记录或者其他敏感数据。

如果问题确实依赖私有内容，可以替换成等价的脱敏例子，只说明数据结构和行为。我们更关心系统发生了什么，不需要看到真实秘密。

## 怎么反馈

优先使用仓库里的 **Alpha memory feedback** Issue 模板。一般安装 Bug 也可以直接开普通 Issue。

如果你分不清这是 Bug、Alpha 暂未支持的能力，还是设计问题，也可以提交。写清楚“我原本预期什么、实际发生了什么”，剩下的分类之后再做。

Public Alpha 招募入口：<https://github.com/yuzi001a/hippocampus-memory/issues/1>

## 这轮 Alpha 成功的标准

不是证明 Hippocampus 已经“解决了记忆”。

这一阶段只要做到四件事就已经有价值：

1. 已声明支持的持久化路径能在作者之外的机器上真实跑起来；
2. 长期使用暴露出哪些召回会过期、污染、重复或者误导；
3. 安装和配置到底哪里麻烦，由真实用户证明，而不是我们自己猜；
4. 下一轮架构变化主要由真实失败驱动，而不是继续增加推测性的边缘场景。

这就是一次合格的 Alpha。

# 记忆插件的完整设计哲学

我认为，要完整回顾这个项目，不能只从 Hippocampus、Observer、向量检索或者 Hermes 插件架构讲起。那样容易把我们做过的技术工作误认为项目本身。

**我们真正想做的，是让 Agent 拥有一个不依附于模型、不依附于客户端、不依附于会话、不依附于某一家 AI 服务商的、属于用户自己的过去。**

这句话是整个项目的出发点，也是判断所有技术方案是否正确的最高原则。

我们的目标不是做一个聊天记录搜索工具，也不是做一个能够不断往数据库里写入信息的 RAG 系统，而是建立一种认知连续性基础设施（Cognitive Continuity Layer）。

它要解决的问题是：

- Agent 换了模型，仍然知道过去发生过什么。
- Agent 换了客户端，仍然能延续之前的工作。
- Agent 换了设备，仍然能够获得共同的长期记忆。
- Agent 开启了新会话，不必让用户重新介绍自己、项目和历史决策。
- Agent 经历了足够多的交互，能够从经历中总结经验、修正认知、淘汰错误认识。
- Agent 面对当前问题时，能够知道什么时候需要回忆、回忆什么，以及什么时候不应该回忆。

这里有一个特别重要的区别：

**我们要共享的是记忆，而不是会话；要共享的是认知基础，而不是让所有 Agent 变成同一个执行实例。**

这也是我们提出 Shared Brain + Local Bodies 的原因：多个设备、多个 Agent、多个 Runtime 可以共享一个长期记忆体系，但各自拥有独立的会话、工具、执行环境和工作状态。

## 一、为什么要做这套系统：从记住对话到继承过去

项目最初有两个现实问题。

第一，Honcho 虽然提供了记忆能力，但自部署、国产模型、Embedding 和 Reranker 的适配存在阻力，需要改源码才能满足我们的需求。

第二，使用 Hindsight 时，出现过度召回、旧记忆污染当前对话的问题。记忆明明是为了帮助 Agent，最后却让 Agent 被过去的错误和无关信息牵着走。

这让我们逐渐明确：**记忆系统的竞争力不是存储多少信息，而是能否让 Agent 在正确的时刻继承正确的过去。**

后来我们又把这个认识推进了一步：

**生成即即时存在。**

我们不是在给一个始终存在的主体补一块硬盘。Agent 每次生成时，都会依据当前输入和被召回的过去形成新的判断；这次生成又可能成为下一次生成的经历。

因此，记忆并非生成之外的附属数据库，而是参与连续生成的基础设施。

这也决定了我们的产品目标不是简单的 Memory Database，而是 Cognitive Continuity。

## 二、记忆的本体：不能把所有东西都叫作记忆

我们早期用过一个很重要的抽象：迹、碑、印，分别对应不同层次的记忆。

**迹（J）**

经历与证据

保存发生过什么，尽可能保留原始对话、时间、角色、来源和上下文。

它回答：当时究竟发生了什么？

**碑（B）**

事实与知识

从经历中提取具体事实、稳定认识、项目知识和主题关系。

它回答：从这些经历中，我们知道了什么？

**印（Y）**

身份与叙事

长期形成的身份认识、关系变化、判断方式和行为基线。

它回答：我是谁，我们如何变化，我通常怎样判断？

这三层不是三个互相竞争的数据库，而是三个不同的认知层次。后续物理架构演变为 `conversation_stream`、`qa_pairs`、`topics`、`observation_notes`、`yin` 等对象，但原有职责没有因此消失。

这里有几条不能破坏的原则。

**1. 原始经历是真值源，模型总结不是原始事实。**

我们采用 source-preserving 思路：

- 原始 conversation/message 是经历的事实来源。
- QA 是对话事实的结构化表达。
- Topic 是跨多段经历形成的主题归纳。
- Observation 是观察者对近期经历的阶段性理解。
- Yin/E1 是更长期的身份和叙事理解。
- Explicit Memory 是用户明确要求保留的记忆。

后面这些都可能出错、过期或需要重建。它们不能反过来取代原始经历。

**2. 记忆的摘要不能冒充证据。**

Topic 可以告诉 Agent 某个项目经历了哪些变化，但如果用户问某个具体决定是谁作出的、什么时候作出的，就应该能够沿着：

`Topic → Topic Entry → QA → 原始消息`

回到证据。

综合事实不能为了方便而伪造一个单独的 QA 来源。

**3. 不同层次的记忆不能混为一谈。**

用户长期偏好、项目当前状态、一次临时决定、某个具体事实和模型的推断，生命周期完全不同。

例如：

- 用户明确说以后回答尽量简洁：可以形成长期偏好。
- 某项目目前采用方案 B：属于有适用范围和时效的项目状态。
- 某次讨论曾考虑方案 A：属于历史经历。
- 模型认为用户可能偏好 A：只能算推断，不能升级为用户确认事实。

这是防止记忆系统逐渐把自己的推断当成用户事实的根本措施。

## 三、记忆形成：先保留经历，再慢慢理解经历

我们最终认可的不是收到消息后立即调用大模型，生成一张永久记忆卡，而是分层、异步的形成机制。

- **原始经历进入消息河**：Conversation Stream · 可靠持久化
- **结构化提取**：QA、事实、来源、时间及角色
- **观察与巩固**：Observer、Topic、关系与变化
- **长期认识**：Yin/E1、用户明确记忆、项目知识
- **进入可召回体系**：自动预取或主动查询

这是逻辑上的职责链，不意味着每条消息都必须经过所有阶段，也不意味着所有阶段同步执行。

这里有一个非常重要的工程哲学：**先落库，后加工。**

原始消息一旦可靠保存，后续 Observer、Embedding、LLM、主题聚类等处理即使失败，也不应该导致经历丢失。

具体来说：

- 原始消息写入与后台处理任务建立可靠关联。
- 后台任务可以重试。
- 重复事件不能制造重复记忆。
- 中途崩溃后能够恢复。
- 派生数据可以根据原始来源重新生成。
- 处理游标不能在结果尚未可靠保存时提前推进。

我们甚至把这件事作为项目的基础优先级：先解决不丢、不重、不乱、不泄露、可恢复，再追求更聪明的记忆。

这也是为什么我们保留 PostgreSQL/pgvector 和 Core + Adapter 架构，没有为了追求新颖而反复更换底层存储。

## 四、记忆巩固：Observer 不是聊天摘要器

Observer 的核心任务不是每隔几轮把对话压缩成一段摘要。

它要做的是：观察新产生的经历，理解与已有认识的关系，并更新持续存在的记忆。

例如，一个项目经历了以下过程：

- 最初提出方案 A。
- 讨论中发现 A 有问题。
- 用户决定改用 B。
- 后来 B 又经过一次调整。

普通摘要容易把这些内容全部压在一起，最后得到一个同时包含 A、B 和调整意见的混合叙述。

Observer 应当理解它们之间的变化关系，而不是简单地把文本越写越长。

我们逐步形成了几个要求：

1. 新 QA 是观察的输入，不是旧摘要的替代品。
2. Topic 是持续更新的主题归纳，不是独立于证据的事实源。
3. Observation 应当能够跨处理窗口保持连续性。
4. 印的生成必须控制长度，不能静默截断。
5. 压缩失败时不能假装成功，更不能推进游标造成数据丢失。
6. 发生纠正时，受影响的旧派生内容要失效或重新生成。

历史上确实尝试过滚动全量印、人格层与当轮快照分离等方案。后来经过实际比较，主线重新确定为单一滚动 Observation Note 配合 E1 压缩，同时保留独立的人格层。不能把曾经尝试过的每种结构都当成现行设计。

更深一层，我们希望记忆具有真正的演化能力：

- 新事实可以补充旧事实。
- 明确纠正可以替代旧认识。
- 过期认识可以降级或失效。
- 重复出现的经历可以巩固某种稳定认识。
- 没有足够证据的推断始终保留不确定性。
- 用户能够查看、纠正和回退错误的派生认识。

**记忆不是越积越多，而是越经历越准确。**

## 五、召回：不是每一轮都回忆，而是在认知需要时回忆

这是整个项目最有辨识度的设计思想之一，也是我们后来单独提出 Cognitive Recall Loop（CRL）的原因。

传统记忆插件的逻辑通常是：

`收到新消息 → 检索历史 → 注入上下文 → 生成回答`

它有一个根本缺陷：把聊天轮次当成了认知周期。

但一个 Agent 可能连续工作几十轮，中间经历多次假设变化、工具验证、任务切换和重要决策。也可能只聊了一轮，就发生了一次非常重要的认知变化。

因此我们明确提出：

**Turn ≠ Cognition Cycle。**

一次认知循环可以是：

- **Recall**：回忆相关经历
- **Think**：结合当前问题推理
- **Observe**：观察工具结果和新证据
- **Recall again**：必要时再次回忆

`Recall → Think → Observe → Recall`，是我们提出的认知循环，而不是固定的聊天流程。

例如，Agent 正在排查一个程序故障：

1. 它回忆起以前遇到过类似错误。
2. 根据过去的经验提出假设 A。
3. 执行工具，发现实际错误码与 A 不符。
4. 这时应该再次回忆，找出过去处理过的同类错误，而不是等用户发下一条消息才检索。
5. 根据新证据修正判断，继续工作。

这就是我们想要的主动记忆能力。

### 1. 认知事件，而非轮次计数

CRL 原型中的事件类别包括：

| 事件 | 含义 |
| --- | --- |
| `HYPOTHESIS_CONFLICT` | 新证据与现有假设冲突 |
| `NEW_ENTITY` | 出现新的重要实体 |
| `PHASE_CHANGE` | 任务进入新的阶段 |
| `CONTEXT_GROWTH` | 上下文出现明显增长 |
| `HIGH_IMPACT_DECISION` | 出现重要决策 |
| `EXPLICIT_MEMORY_CUE` | 明确要求回忆某段过去 |
| `TOOL_OBSERVATION` | 工具结果产生值得重新回忆的信息 |

其中，前五类是主要认知事件，后两类是明确提示和工具观察入口。

注意，这七种是 CRL v0.1 可核实的事件类型，不应直接与架构文档中另行提及的“五信号”定稿混为一套。

### 2. Hippocampus 和 CRL 必须分离

这是我们反复强调的架构边界。

- **Cognitive Recall Loop**：决定何时回忆、为什么回忆、是否值得再次回忆。
- **Hippocampus**：负责记忆保存、组织、检索、来源追踪和返回相关经历。

CRL 是认知触发与编排层，Hippocampus 是记忆基础设施。

Hippocampus 不应该吞并 Agent 的推理、工具调用、任务编排和 Session 管理。

反过来，CRL 也不应该重新建设一套记忆数据库。

两个系统通过清晰接口合作：CRL 产生事件，规则判断是否需要回忆，然后调用 Hippocampus 已有的召回能力。

CRL v0.1 已经作为独立研究原型发布，具有 `CognitiveEvent`、`RecallPolicy`、`MemoryRetriever` 和 `InMemoryRetriever` 等基础协议。但事件自动检测、真实 Agent/Hermes Hook、V3 适配和召回后的状态修订，并不能据此认定已经完成生产集成。

### 3. 自动召回必须有限度

我们不希望 Agent 在一个长任务中无限次回忆。

原型接入计划给出了初始控制规则：

- 每个用户回合最多两次额外自动召回。
- 同一个事件不能重复处理。
- 常规冷却时间为 30 秒。
- 用户明确要求搜索历史，不受自动召回次数限制。
- 没有新结果、结果重复或 Provider 失败，当前任务继续执行。

这不是为了限制 Agent 的智能，而是为了防止重复召回、上下文膨胀和不必要的模型成本。

### 4. 还必须区分另一套触发机制：Observer 的四信号

这里容易混淆。

Observer 的写入触发不是 CRL 的认知事件触发。我们在 2026 年 8 月 3 日定稿过一套四信号机制：

| 信号 | 触发条件 |
| --- | --- |
| `token` | 全局未观察 QA 字符达到 50,000 |
| `count` | 全局未观察 QA 达到 100 条 |
| `new_session` | 新会话至少积累 5,000 字符 |
| `pause` | 距离任何新 QA 已绝对空闲 4 小时，且仍有未观察内容 |

触发后有 8 分钟防抖，单次最多观察 30 条 QA。经过 30 天真实数据验证，平均约 2.8 次/天。

这套机制解决的是：什么时候应该让 Observer 整理新经历。

而 CRL 解决的是：什么时候应该让 Agent 在当前任务中重新回忆。

两者不能合并成一个触发器。

还有一个容易混淆的数字：**8 秒是自动预取的响应预算，8 分钟是 Observer 的防抖时间。** 前者保证记忆系统不能拖住 Agent，后者减少不必要的观察者调用。

## 六、召回策略：记忆找到了，不代表应该注入

我们从 Hindsight 的过度召回问题中吸取的教训是：

相关不等于有用，有用也不等于现在就应该注入。

因此，我们明确区分两个入口。

**Prefetch：被动预取。**

在新会话或当前任务需要时，自动选择少量高信号内容，提供必要的身份、项目状态和历史背景。

它追求的是：

- 无感知。
- 低延迟。
- 高相关性。
- 低干扰。
- 可控 Token 消耗。

**Search：主动检索。**

用户明确要求找历史资料、查某个决定、回顾某次经历时，允许进行更深入的查询，返回更完整的事实和证据。

两者可以共享底层召回算法，但不能共享消费语义。

### 召回不是单一向量 Top-K

我们的检索思路是多路召回，再进行融合和预算分配。

```text
当前问题（Query Context）
  ├─ 关键词召回
  ├─ 向量召回
  ├─ QA 原文证据
  ├─ Topic 主题
  ├─ Yin / Notes
  └─ Anchor / 状态背景
        │
        ▼
   RRF 多路融合
        │
        ▼
  可选 Reranker
        │
        ▼
注入预算与完整内容组装
```

历史架构记录中的一组冻结基线是：

| 参数 | 设定 |
| --- | --- |
| RRF K | 60 |
| 时间半衰期 | 30 天 |
| 关键词权重 | 0.5 |
| Vector / QA / Yin / Notes | 1.0 |
| Topic | 2.0 |

这些是当时召回语义的基线，不应未经验证就当成永远不可调整的参数。

另外还有一个重要原则：完整单元注入。

不能为了凑够 Token 预算，把一条记忆的关键后半部分截掉，最后只给模型一个残缺结论。要在完整记忆单元之间分配预算，并记录各路召回的淘汰原因。

**最终优化目标不是让更多记忆进入上下文，而是让真正有帮助的记忆进入上下文。**

## 七、时间、冲突、纠正和遗忘：记忆必须有生命周期

这是我们从普通向量记忆走向真正长期记忆的关键一步。

如果只把新信息不断写进去，即使召回算法再好，也会出现一个问题：过去的事实、现在的事实和已经失效的决定同时存在，模型不知道应该相信谁。

我们希望建立的机制是：

### 1. 事实不是永远有效的

同一事项可能经历：

`产生 → 确认 → 更新 → 被替代 → 归档`

例如：

| 时间 | 记录 | 状态 |
| --- | --- | --- |
| T1 | 项目采用方案 A | 当时有效 |
| T2 | 发现方案 A 存在问题 | 需要调整 |
| T3 | 用户决定采用方案 B | 当前有效 |
| T4 | 询问为什么曾经采用 A | 历史仍然可查 |

旧事实不是简单删除，而是保留历史和来源，同时停止把它当作当前事实。

### 2. 用户纠正具有特殊地位

我们明确过：

- 用户明确表达的事实和纠正，优先于模型推测。
- 模型总结不能反过来覆盖用户原话。
- 新消息不能仅因为时间更新就自动覆盖旧事实。
- 必须确认是否是同一个项目、同一个事项、同一个适用范围。
- 无法确定时保留冲突，不允许向量分数最高的内容自动成为真相。

### 3. 纠正必须传播

只改一张显式记忆卡是不够的。

如果 Observer、Topic、Yin 里面还保留着旧结论，下一次自动预取仍然可能把错误带回来。

因此，我们设计的纠正流程是：

1. 保存用户的新纠正及原始来源。
2. 建立新旧认识之间的替代关系。
3. 找到依赖旧认识的派生内容。
4. 让受影响的旧派生内容失效。
5. 按需重建。
6. 无法可靠重建的内容先停用或标记待复核。

最重要的是，即使后台 LLM 或 Embedding 服务失败，用户的纠正也必须已经可靠保存，不能因为重建失败而重新启用旧错误。

### 4. 遗忘不是删除历史

我们追求的是有选择地降低旧记忆对当前生成的影响，而不是把过去抹掉。

- 失效事实可以保留供历史查询。
- 过期内容不应继续作为当前结论注入。
- 重复内容可以合并，但不能破坏原始证据。
- 低价值内容不必永久占据主动召回位置。
- 用户有权查看、纠正、归档和删除自己的记忆。

这也是我们提出时间感知召回、版本关系、失效传播和回退机制的原因。

## 八、系统架构：共享大脑，独立身体

我们不希望 Hippocampus 永远只是 Hermes 的一个插件。

真正的架构应该是：

- **Hippocampus Core**：独立记忆运行时 · 统一记忆模型 · 统一数据真值
- **Adapters**：Hermes Adapter / DSH Adapter / pi Adapter
- **用户拥有的长期记忆**：PostgreSQL / pgvector · 可迁移 · 可恢复

上面是目标适配结构，不代表三个宿主目前都已经达到同等生产支持程度。

### 1. Core 与 Adapter 分离

Core 负责：

- 消息接收与持久化。
- 记忆形成与巩固。
- 检索和召回。
- 显式记忆管理。
- 删除、导出和恢复。
- 后台处理与生命周期管理。

Adapter 负责：

- 接收宿主的消息和事件。
- 识别 Session 和消息身份。
- 调用 Core。
- 将召回结果放入宿主上下文。
- 遵守宿主自身的启动、关闭和资源管理机制。

不能让 Hermes 的插件直接操作数据库表，也不能让 Observer 自己另建一套绕开应用服务的写入路径。

我们后来还明确了正式的 `MemoryProvider` 接口。Hermes 是第一个主要宿主，但不应该成为整个记忆系统的架构边界。

### 2. Shared Brain + Local Bodies

这个概念是我们在多设备部署讨论中形成的。

假设：

- 台式机运行 Hermes。
- 笔记本运行 pi。
- 另一台机器运行 DSH。
- 以后还有其他 Agent。

它们可以访问同一个长期记忆体系，但不应该共享同一个 Session。

因为不同设备的模型、Harness、工具、工作目录、执行权限都可能不同。

共享的是：

- 用户长期认识。
- 项目档案。
- 重要决策。
- 历史经历。
- 任务进度和必要的 Checkpoint。
- 跨会话可复用的知识。

不共享的是：

- 各设备的当前 Session。
- 本地工具运行状态。
- 当前执行环境。
- 不应跨 Agent 暴露的私有信息。

**记忆可以共享，执行状态必须有边界。**

而且多 Agent 并发写入不能只靠给数据库增加一个 namespace 就宣告安全。必须解决身份、权限范围、幂等、冲突和并发控制。初期以独立实例或明确的单写入者为主，真实需求出现后再推进多写入者。

### 3. 模型和服务商无关

我们不想被某个模型供应商锁死。

因此架构上要把：

- LLM。
- Embedding。
- Reranker。
- 存储。
- 锁。
- 时钟。
- 队列。

做成可以替换的依赖接口。

模型更换不应该要求重建整个记忆系统；Embedding 更换则需要识别模型、维度和向量指纹，避免不同模型生成的向量混用。

用户自己选择模型、自己提供 API Key、自己控制部署和数据。

这就是 BYOK、Provider Agnostic 和 Self-hosted 的意义。

## 九、可靠性和隐私：过去不能因为插件出故障而消失

这部分我们曾经投入了大量工程工作，因为它决定了用户敢不敢把自己的长期经历交给系统。

我把它归纳成六条。

**1. 原始经历不能丢。**

LLM、Embedding、Observer 任何一个服务故障，都不能影响原始经历的持久化。

**2. 同一经历不能重复。**

相同消息重试、进程重启、事件重放、Adapter reload，都不能制造重复记录。

**3. 派生加工必须可以恢复。**

处理任务需要明确的身份、状态、游标和回执。失败后能够重试，不能靠猜测后台到底做到了哪一步。

**4. 实时召回不能拖垮 Agent。**

8 秒自动预取预算是我们明确记录过的铁律。超时就跳过记忆注入，让宿主继续执行。

这里要区分两种故障处理：

- 检索、Embedding、Reranker 等可选能力失败：及时降级，不能拖垮 Agent。
- 原始经历没有可靠保存：不能假装已经记住，必须明确报告失败或使用可靠的持久化恢复路径。

**5. 私人记忆不能泄露。**

本地优先、默认不记录私人正文到普通日志；密钥不进入配置输出、诊断包或公开仓库；导出和删除要有明确边界；远程接口必须有认证和权限控制。

**6. 记忆必须能够带走。**

用户更换机器、数据库或宿主，应该能导出和恢复自己的过去。

导出至少应携带原始消息、角色、时间、来源、项目范围、用户明确记忆和纠正关系。向量、摘要等派生数据可以重新构建，不应成为迁移的唯一载体。

更重要的是，不能把 API Key、数据库密码等运行凭据一起打包。

这六条实际上是我们对记忆系统最基本的信任承诺。

## 十、评测哲学：不能只证明检索成功，要证明记忆有用

我们逐渐形成了三层评测思路。

| 评测层 | 要回答的问题 | 典型指标 |
| --- | --- | --- |
| 检索层 | 找到的记忆对不对？ | Recall、Precision、误召回、过期内容 |
| 提炼层 | 从经历中总结得对不对？ | 事实保留、来源完整、遗漏、编造 |
| 存在层 | 记忆真正进入模型后，有没有帮助？ | 回答正确性、连续性、任务完成效果 |

这里的第三层尤其重要。

一张记忆卡的相似度很高，不代表模型能够正确理解它；一段印写得很好，也不代表它能帮助模型完成当前任务。

因此我们一直强调：

**必须测试真实的生产召回与注入路径，而不是只在数据库里测试向量相似度。**

### 我们真正关心的指标

1. Recall Precision：找到的是否真有用。
2. False Recall：是否把不相关的过去带进来。
3. Stale Memory：是否把失效事实当成当前事实。
4. Cross-session Continuity：新会话能否接续旧任务。
5. Source Fidelity：是否能够追溯原始经历。
6. Correction Effectiveness：纠正后旧错误是否真正停止传播。
7. Context Cost：为了这次记忆花费了多少 Token。
8. Latency：记忆有没有拖慢 Agent。
9. Task Utility：是否减少重复劳动、错误尝试和用户重新解释的成本。

LoCoMo 等基准可以用于重要算法变化时的对照，但不能代替真实用户使用。

评测还必须与生产记忆隔离。不能把评测问题和标准答案偷偷写进记忆库，再用它们证明检索效果。

### 我们不追求每条记忆都排第一

真正合理的评价是：

- 该回忆的时候有没有回忆？
- 不该回忆的时候有没有克制？
- 召回的内容能不能解决当前问题？
- 发生纠正后有没有真正改变？
- 失败时能不能定位到保存、提取、检索、筛选、注入或模型使用的哪一环？

这比单纯追求某个 `Recall@K` 数字更符合产品目标。

## 十一、知识治理：自动学习不等于自动永久记忆

我们还形成过一个很重要的延伸原则：

**Capture aggressively, promote conservatively。**

即大胆捕获，谨慎晋级。

Agent 工作中可能发现：

- 用户纠正。
- 一个反复出现的错误。
- 一个有效的操作方法。
- 某个项目的架构决策。
- 一条可能跨项目复用的经验。

这些都值得先保留下来，但不代表它们应该立即进入永久知识体系。

我们区分三个阶段：

| 阶段 | 含义 |
| --- | --- |
| `LEARNING_EVENT` | 一次值得记录的学习事件 |
| `LEARNED_ARTIFACT` | 保存原始证据、上下文和初步认识 |
| `ACTIVE_KNOWLEDGE` | 经过核实、分类、提炼后真正能够指导未来行为的知识 |

晋级前应考虑：

- 是否重复出现？
- 是否有真实证据？
- 是否仍然有效？
- 是否已有更权威的知识来源？
- 应该放在哪里？
- 是否真的需要主动加载？

知识的归属也必须明确：

- 用户长期偏好 → 用户记忆。
- 项目架构和决策 → 项目文档、ADR。
- 当前项目进度 → 项目状态。
- 跨项目通用操作方法 → 通用 Skill。
- 历史事故和实验 → 历史档案。

一个事实只能有一个权威归属，不能在用户记忆、Skill、项目文档和其他地方反复生成相互矛盾的副本。

这实际上是记忆系统长期保持正确性的另一半：不仅要会记，还要知道应该把什么记在哪里。

## 十二、我们明确不想做什么

这些非目标与正面设计同样重要。

| 不做的事情 | 原因 |
| --- | --- |
| 不做聊天记录搜索器 | 目标是认知连续性，不是全文搜索 |
| 不按每轮对话机械召回 | 轮次不等于认知事件 |
| 不把所有信息压成一份超长摘要 | 不同信息需要不同生命周期 |
| 不让模型总结取代原始事实 | 防止错误逐层传播 |
| 不让历史记忆支配当前判断 | 当前证据和用户纠正必须有效 |
| 不让记忆插件承担 Agent 全部推理 | 保持基础设施边界 |
| 不绑定某个模型供应商 | 用户应能自主选择 |
| 不默认启用多 Agent 并发写入 | 先解决隔离、幂等和冲突 |
| 不为图谱而图谱 | 必须证明独立召回收益 |
| 不为了功能丰富而建设庞大管理后台 | 先把核心记忆链路做好 |
| 不承诺绝对正确 | 记忆必须允许质疑、纠正和回退 |

这里尤其要强调图谱。

我们确实非常重视人脑式意义关联：从一段经历联想到另一段表面上不相关、实际上存在联系的经历。

但是，过去测试过的共现图和向量语义图，并没有证明它们作为独立召回通道具有足够的增益。因此我们砍掉了它们的主注入路径。

这不代表放弃意义关联的愿景，而是拒绝把一个没有效果的实现强行留在主链路。

## 十三、主动记忆与被动记忆：两种机制不能混为一谈

这是容易被忽略、但非常重要的一条设计。

我们曾经讨论过 MOC/F1 手帐和被动记忆插件的关系。

两者承担不同职责：

| 机制 | 记录什么 | 典型用途 |
| --- | --- | --- |
| 主动记忆 | 用户明确要求保存的内容 | 项目当前状态、重要事项、手工整理的知识 |
| 被动记忆 | Agent 在真实交互中经历的事情 | 自动记录对话、发现事实、观察变化 |
| 长期身份记忆 | 长期形成的稳定认识 | 用户偏好、关系、判断习惯、行为基线 |

主动记忆不是被动观察者提炼出来的 Topic，不能因为它们都叫 Memory 就合并生命周期。

我们曾经明确过：两条路径分别维护自己的数据和更新规则，最终在候选召集、融合和上下文注入环节相遇。

这样既保留用户主动控制的能力，也不会让自动观察覆盖用户明确保存的内容。

## 十四、历史演化中，哪些方向值得保留，哪些不能复活

这个项目经历过多轮架构实验。不是所有尝试都成功，也不是所有暂时没有进入主链路的设计都应该被遗忘。

我把比较重要的结果整理如下。

| 设计 | 历史结论 | 当前认识 |
| --- | --- | --- |
| 消息河、事件溯源 | 已实现 | 核心基础，不能退化 |
| 迹、碑、印 | 已实现其职责 | 仍然是记忆本体的核心抽象 |
| Topic 成为一等公民 | 已实现 | 主题及证据回链继续保留 |
| Observer | 已有生产实现 | 仍需完善更新、纠正和版本语义 |
| E1/Yin | 已有实现 | 长期身份与叙事层 |
| Hybrid Recall、RRF | 已有实现 | 继续改善选择和注入 |
| Effective Pool | 独立实现搁置 | 部分职责已被其他组件吸收 |
| TKG 时序事实层 | 实现过程中断 | 设计没有被实验否定，值得重新审视 |
| 共现图独立召回 | 实验否定 | 不恢复原有注入路径 |
| 向量语义图独立召回 | 实验未证明独立收益 | 保留离线分析价值 |
| 意义关联图 | 尚未真正实现 | 愿景保留，不能把旧实现当成果 |
| 句子级印索引 | 暂缓 | 有潜在价值，等待真实需求 |
| Session Checkpoint、工具输出卸载 | 未完整闭环 | 长任务连续性仍值得推进 |
| DBSCAN 大规模聚类 | 实验否定 | 不恢复旧聚类方式 |
| `cl_*` 压缩摘要聚簇 | 已退役 | 原始 QA 和 Observer 提炼更符合主线 |

特别说三个容易误解的地方。

**第一，Effective Pool 并不是所有职责都消失了。**

它原来负责高信号上下文、稳定锚点和项目状态的集中管理。后来其中不少职责被分散吸收到身份块、态势概览、Observation、动态尾巴、Topic/QA 召回和注入预算中。

所以我们不应该为了恢复旧设计而重新造一个大池子。

**第二，TKG 不是被证明没有价值。**

它曾经解决过事实随时间变化、旧状态被新状态替代的问题，但在后续重构中发生实现断档。它属于设计遗失，而不是实验否定。未来应该恢复其时序语义，而不是照搬旧数据库结构。

**第三，图谱实验失败，不等于意义关联的研究方向失败。**

过去的共现图实际上主要表达时间邻近，语义图又与现有向量召回高度重叠。我们砍掉的是没有独立收益的实现，不是跨时间、跨主题的非显然意义联想这个目标。

## 十五、当前最需要守住的设计边界

把上述哲学与最近的开发情况结合起来，我认为有几个问题尤其不能混淆。

**1. 记忆保存已经有基础，但长期认知演化不等于已经完成。**

原始经历、QA、Topic、Observer、Yin、混合召回和 Recall V2 都已经有实际实现积累。

但完整的自动认知循环、跨任务导航、长期认识更新及纠正后的全链路一致性，仍然有工作要做。

**2. Observer 必须解决新旧认识如何替代的问题。**

不能只做到新观察不断追加。必须让系统明确知道当前有效的观察是什么、覆盖哪些原始经历、哪些旧认识已被替代。

我们在不同阶段讨论过滚动印和当轮快照两种结构。历史文档对主链形式存在演化和口径差异，不能把某个旧方案直接当成当前代码真值。

真正不变的要求是：观察必须有来源、版本、明确的覆盖范围，旧版本可以追溯，当前版本不能混乱。

**3. 普通 Topic 冲突也需要真正进入状态管理。**

不能只有用户手工创建的显式记忆才有版本关系。项目事实、主题认识和 Observer 总结同样会变化。

但这不意味着马上重写成大型知识图谱。先把一个真实的 A 改 B 场景做好。

**4. CRL 仍然要坚持独立边界。**

它不能为了实现自动召回而变成 Hippocampus 的一部分，也不能因为原型已经发布就宣称生产认知循环已经完成。

**5. 多 Agent 共享需要建立在隔离正确的基础上。**

共享长期记忆，不等于共享所有个人经历，更不等于允许所有进程同时无约束写入。

这些边界与我们之前的开发路线是一致的。

另外，有一个细节需要如实说明：现有架构索引确实把“五信号、触发状态机、消息河、8 秒预算、印哲学”列为核心定稿，但我目前能够核实的资料没有完整呈现那套“五信号”的正式枚举和映射关系。因此，我没有把 Observer 的四个写入触发条件、CRL 的七种认知事件强行拼成所谓正式五信号。这部分应以原始架构定稿为准。

## 十六、最终归纳：我们到底想造一个什么样的记忆系统？

我把整个设计哲学压缩成下面这份原则清单。

### Hippocampus 核心设计原则

从产品定位到工程实现的统一原则：

- **01 记忆属于用户**：不属于某个模型、客户端或 AI 服务商。
- **02 过去必须连续**：让 Agent 换会话、换设备、换模型仍能继承过去。
- **03 原始经历优先**：原始消息是事实源，所有总结都必须可以追溯。
- **04 记忆分层组织**：区分经历、事实、主题、状态和长期身份。
- **05 先保存再理解**：原始经历可靠持久化，智能加工异步完成。
- **06 大胆捕获，谨慎晋级**：记录不等于确认，推断不等于事实。
- **07 记忆持续演化**：支持补充、纠正、替代、过期、归档和回退。
- **08 认知事件触发回忆**：Turn 不等于 Cognition Cycle。
- **09 预取与主动检索分离**：自动注入少而精，主动查询深而全。
- **10 召回必须有预算**：相关不等于有用，记忆不能淹没当前任务。
- **11 共享记忆而非共享会话**：Shared Brain + Local Bodies。
- **12 Core 与 Adapter 分离**：记忆系统不依赖某个 Agent Harness。
- **13 本地优先与开放接口**：自托管、BYOK、Provider Agnostic。
- **14 可靠性优先于智能**：不丢、不重、不乱、不泄露、可恢复。
- **15 以真实任务评价价值**：关注连续性、纠错、任务效用和错误召回。

最后，我认为还有一句比技术架构更重要的话：

**我们不是要让 Agent 记住更多东西，而是要让 Agent 因为拥有自己的过去，逐渐成为一个能够延续、能够学习、能够纠正自己，并且不会反复从零开始的系统。**

这才是 Hippocampus 与普通 Memory Plugin 最根本的区别。

如果以后有人要修改这个项目，我认为可以用三个问题判断方案是否符合初衷：

1. 它是否让 Agent 更好地继承了过去？
2. 它是否让记忆变得更准确、更可控，而不是更容易污染当前判断？
3. 它是否让这套记忆真正属于用户，并且能够跨模型、跨宿主、跨设备延续？

三个问题都回答不了，哪怕增加了很多工具、表和算法，也不一定是在推进这个项目。

这份总结可以作为我们后续审查记忆插件架构、评估 PR 和制定开发路线时的哲学基准。
